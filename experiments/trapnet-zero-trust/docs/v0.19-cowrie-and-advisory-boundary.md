# TrapNet v0.19: Cowrie write-path isolation and optional AI input boundary

**Status: Draft PR only. No production Sonar changes, no public beta approval.**

## Isolated Cowrie trial: actual VPS observation

The production Cowrie image was tested as a **separate throwaway container** on
the VPS: network mode `none`, no published ports, non-root uid, read-only root,
limited CPU/memory/PIDs and private tmpfs for `/tmp` and `/cowrie/cowrie-git/var`.
No production Cowrie config/log mounts or credentials were copied.

The container's internal SSH listener was reachable at loopback port 2222.
**However, Cowrie's JSON log output plugin failed with FileNotFoundError**
because a brand-new tmpfs lacks `var/log/cowrie`. This must **not** be
interpreted as a functioning fully read-only deployment. The disposable trial
container was deleted. A follow-up attempt to exercise startup with an
initialized writable hierarchy was blocked by the runtime safety check and
was **not performed**.

A separate non-mutating `cowrie_workspace.py` checks, without creating files,
that the explicitly private writable workspace has `log/cowrie`, `run`,
and `lib/cowrie` directories, with symlink path components rejected.
Passing this path preflight does not prove that Cowrie starts, writes logs,
persists safely, isolates outbound traffic, or recovers after a power failure.
It must be rerun on the target POSIX staging filesystem.

## Hardened static containment audit

`containment_audit.py` now checks `writable_mounts_scoped` per component:

- Web/edge: no writable *bind*, *volume* or tmpfs mounts declared in Docker
  inspect `Mounts` (Docker's `Tmpfs` settings are **not** covered).
- SSH/Cowrie: only `/cowrie/cowrie-git/var` may be a writable inspected mount.
- Unexpected writable mounts, especially Cowrie's current writable
  `/cowrie/cowrie-git/etc` **configuration volume**, fail.
- No raw Docker inspect output, credentials or network addresses are printed.

The live Cowrie configuration was read-only inspected and shows a writable
root filesystem plus a writable settings volume and a writable var bind mount.
It therefore fails the new acceptance controls. It is **not** authorized for
self-hosted public beta. The inspect audit is intentionally not a penetration
test, firewall check or destruction/recovery drill.

## AI advisory aggregate allowlist

`safe_analysis_input.py` validates the fixed
`trapnet.public-aggregate.v1` coarse category/status/band schema or the
exact approved `trapnet.passive-import.v0.1` wrapper. Unexpected keys,
raw URLs, IP fields, user text, commands, malformed bands, strings with
prompt instructions, and false privacy flags are rejected. Output contains
only fixed-format count bands plus empty allowed actions. There is **no
connection to an actual AI model**, and no Guardian action or firewall change.
No test has established a deployed AI pipeline is prompt-injection resistant.

## Verification and release gates

On Windows, 21 v0.19 Python tests were run: 20 passed, 1 POSIX symlink
creation test skipped because the user has no Windows symlink privileges.
Linux CI must exercise that test. A successful CI still cannot approve Sonar.

Remaining HOLD gates: sanitized, isolated startup with logging fully
operational; no writable config mounts; bounded retained log volumes and
backup/recovery; measured network/egress containment; third-party human
review; release signing and operator approval. The household Stick PC is
not an eligible public honeypot on its existing LAN.
