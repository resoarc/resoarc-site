# TrapNet v0.6: witnessed evidence generations (experimental / HOLD)

## Threat model

A 64 MiB active ledger fills up. Blind truncation/reset loses event IDs, allowing valid older signed events to be replayed. We need a new empty active ledger without discarding an old witnessed evidence generation. This implementation provides **operator-assisted, deliberately non-destructive preparation**, not a safe unattended automatic rotation, a distributed consensus system or a validated disaster-recovery procedure.

Trust chain:

1. Keep each old ledger and `.head` intact in a protected, read-only/off-host archive, after v0.5 offline snapshot.
2. An independent Witness has checked the old ledger and signed its full history; independently pin its last history hash.
3. An **offline archive authority** signs a manifest listing **all** earlier ledger generations, each with exact row count, last digest, witness public key, signed history path, and pinned history tip.
4. Pin the SHA-256 digest of the signed manifest outside HUB administrative control (and the separate archive authority's public key).
5. HUB startup verifies the signed and pinned manifest, EVERY archived ledger against its Witness history, and restores all accepted event IDs and recent receipt times before listening. It refuses corrupt, missing, rolled-back or duplicate archived identities.
6. The active generation contains `ledger.jsonl.archives-required`. HUB refuses to start it without all three parameters `-archives`, `-archive-root`, `-archive-tip`. Supplying archive parameters without this marker also fails.

### Operator workflow (no internet exposure)

**Run this only with a stopped HUB and an isolated off-host Witness. The archive and history must be retained as immutable, distinct backups. Paths in the signed manifest are absolute paths as seen by the HUB when replay is restored.** Ensure the signer can inspect the same mounted read-only archive. The archive private key must NEVER be copied to HUB or included in this source repository.

1. Stop HUB, investigate any stale lock, back up both current ledger and `.head`. Create a v0.5 verified snapshot with `cmd/snapshot`.
2. On a physically/logically separate machine, attest the complete snapshot using `cmd/witness -mode attest`; independently publish/pin its exact Witness `expected-tip` and trusted public key. Never bootstrap a new history for an existing identity.
3. Create an unsigned JSON manifest. Example below is schematic and requires real absolute paths and cryptographic digests:

```json
{
  "schema":"trapnet.archives.v0.1",
  "generation":2,
  "segments":[{
    "ledger":"/secured/read-only/snapshot-0001/ledger.jsonl",
    "history":"/secured/witness/history-0001.jsonl",
    "witness_public":"/secured/witness/public-0001.hex",
    "expected_tip":"64-lowercase-hex-witness-tip",
    "rows":1,
    "digest":"64-lowercase-hex-ledger-digest"
  }]
}
```

For generations 3+, include *every* earlier segment, in order, and set `generation = number of segments + 1`. Do not omit older evidence to reclaim space. Witness history is scoped to ONE ledger generation; new ledger generations require a new externally pinned witnessed history.

4. On the OFF-HUB signing machine, use `go run ./cmd/archive-sign -mode sign -manifest unsigned.json -key offline-archive-private.hex -out archives.signed.json`. The printed manifest hash must be pinned independently, not simply left next to the HUB ledger.
5. With the public archive key and pinned hash, verify *all* required inputs using `go run ./cmd/archive-sign -mode verify -manifest archives.signed.json -pub archive-public.hex -tip <pin> -active /path/to/next/ledger.jsonl`.
6. Create the next active generation **without touching the original**: `go run ./cmd/archive-sign -mode prepare -manifest archives.signed.json -pub archive-public.hex -tip <pin> -out /path/to/generation-0002`. The new directory must not exist beforehand. The tool checks all witnessed ancestors then atomically creates an empty ledger, empty integrity head and mandatory archive sentinel.
7. With a separately protected service configuration carrying the public root and pinned manifest hash, point HUB at the new active ledger. Example: `hub -ledger /path/to/generation-0002/ledger.jsonl -archives /path/to/archives.signed.json -archive-root /path/to/archive-public.hex -archive-tip <independently pinned sha256>`.
8. Before allowing even isolated test traffic, confirm the old signed report returns HTTP 409 and new signed reports work. Reboot and repeat. Store the previous generation's service config, off-host backup and incident recovery plan independently.

### Important security limits

- If HUB root can erase the marker *and replace the independently pinned launch configuration*, it may start a misleading genesis. Do not mistake a locally stored marker for a hardware trust root. Monitor/configure service startup outside HUB administrative control.
- Absolute paths, witness histories and signatures cannot guarantee the external archives are durable, off-host, honestly observed, or free from a compromised signing authority. Cryptography verifies byte continuity, not maliciousness of network traffic.
- Each startup rescans archived evidence (max 32 generations, max 1 GiB total); this is intentionally simple but not yet appropriate for massive deployments. Keep archival storage read-only and monitor latency/disk quota.
- Compaction, deletion, asynchronous rollover, automatic migration, credential provisioning, root-key rotation, background reconnection and public ingestion remain disabled/unimplemented.
- A clean exit during an offline snapshot is not an electrical power-loss simulation. Run real disk-full, crash, fsync and backup recovery drills on isolated machines before operational rollout.
- Fail CLOSED on any error. Investigate and restore from independently pinned backups; never use an unsigned history bootstrap or delete missing evidence to make validation pass.

### Tested locally

- Old signed reports remain rejected with HTTP 409 across a new generation, after HUB restart; fresh reports are accepted.
- Witnessed ledger modifications, missing signed history, incorrect pinned manifest SHA-256, manipulated signed metadata and incomplete generation lists fail validation.
- Preparing an existing destination fails without overwriting it; missing/omitted archive arguments are rejected when a rollover sentinel exists.

**Release gate:** Draft PR only. This is a safe development primitive, not finished automatic rotation and not permission to run exposed honeypots or deploy Guardian publicly.
