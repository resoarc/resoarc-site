# TrapNet v0.8: 実プロセス連携・障害復旧ブラックボックス試験

2026-10-27 / Development-only. **No deployment approval.**

## What ran
- Five independent **OS Sensor processes**, each with a different generated Ed25519 identity, posted synthetic observations to a separate running HUB process.
- One Guardian process verified operator-signed informational feed independently.
- Offline revocation signing and external Witness were invoked as separate binaries.
- All ingress **127.0.0.1:8788** only. Test material is temporary and never enrolled into public TrapNet.
- The test reports **32 checks (8 binary builds + 24 black-box assertions)**. These are checks, not 32 independently audited security properties.

## Run

```sh
cd experiments/trapnet-zero-trust
python3 lab/blackbox_lab.py --source . --out trapnet-lab-results.json
```

The same script executes in GitHub Actions `unit-security-tests`. A summary JSON artifact is uploaded without keys, raw event payloads, private data, or witness private keys.

## Assertions
1. Five distinct Sensor processes post signed synthetic observations (202), and five rows persist.
2. A **registered compromised Sensor may lie**. The HUB only stores `received_unverified` and does **not** auto-block.
3. HUB refuses non-loopback bind, malformed body and Content-Type, tampered signatures (403), unknown identity (403), and replay (409).
4. Hot offline-signed revocation denies compromised identity, preserves an unaffected identity; stale/missing signed revocation causes fail-closed 503.
5. Guardian accepts separately signed feed and rejects tampered or older feed.
6. Force-killed HUB leaves a stale writer lock; automatic restart is refused.
7. A separate off-HUB **copy** of evidence and its checkpoint is witnessed and pinned; a read-only recovery audit returns `may_start_hub=false`. Explicit lock clearing is performed **only in temporary lab files** after verifying evidence.
8. Restarted HUB rejects replay, and Guardian can still verify its offline feed.

## Results
- 32/32 passed in the local sandbox.
- GitHub Actions CI status must be checked on the current commit; local success is not CI success.

## What this does NOT test
- Five different machines/VMs/administrators: **not implemented**. All five Sensor processes share a single OS and loopback network namespace.
- Actual VLAN/firewall isolation and network egress denial.
- Real power failure, real disk-full behavior, trusted time, multi-operator Sybil resistance, external witness key custody, or malicious privileged HUB host compromise.
- Security against malicious or fabricated **validly signed** observations; cryptographic authentication alone cannot show observation truth.
- Public node onboarding, privacy compliance, software update security (TUF), or auto-blocking.

## Safety and next gate
- The experimental HUB rejects any bind address other than `127.0.0.1:8788`; Sensor only reports to this address.
- No production installation, port-forwarding, live honeypot, automated blocking, remote commands, or public enrollment.
- Next: independent network namespaces/VMs in an authorized isolated lab, egress/LAN reachability validation, hub-death and witness-key custody drill, consent/privacy review, and physical power/storage fault tests.

**A validated loopback integration test is not a production zero-trust network.**
