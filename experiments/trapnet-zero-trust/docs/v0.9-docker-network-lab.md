# v0.9 five Docker namespace isolation lab (experimental only)

This lab complements v0.8 one-host loopback testing. It runs **five real Sensor Linux processes** in separate Docker network namespaces, each attached to its own `docker network create --internal` bridge. The single HUB container is attached to all five bridges. No container port is published to the Docker host or Internet. The Guardian runs with `--network none` and only accepts an offline Ed25519-signed feed.

## Network topology

```text
 sensor-0 -- internal bridge 0 --┐
 sensor-1 -- internal bridge 1 --┤
 sensor-2 -- internal bridge 2 --┼-- HUB container (loopback-only Go HUB)
 sensor-3 -- internal bridge 3 --┤                 |
 sensor-4 -- internal bridge 4 --┘        LAB-ONLY TCP relay
                                           (no host port)
 Guardian container: --network none, separately signed offline feed
```

The Go HUB and Sensor still refuse non-loopback addresses in their normal binaries. `lab/netlab_bridge.py` temporarily relays loopback traffic **within** the named Docker-only networks. The relay must never be exposed outside these disposable test networks, delivered as an end-user component, or run in production. It requires an explicit lab marker and the orchestration script creates `--internal` bridges and verifies no published HUB ports. Docker host administrators retain full access, so this is not protection against a hostile host.

## Repeatable test

Run on a disposable Linux Docker host with an operational Docker Engine, Python 3 and Go. This test can pull the public official `python:3.13-alpine` image. Do not run it on the user's production VPS, home router, NAS or network.

```sh
cd experiments/trapnet-zero-trust
python3 lab/docker_isolation_lab.py --out lab/netns-results.json
```

On failure, the harness exits nonzero and still attempts to remove only its own randomly named containers and networks. The result JSON contains no private signing keys. It also runs as a standalone GitHub Actions job in the existing experimental workflow.

## Assertions

- Five distinct independently generated Ed25519 Sensor identities, with separate read-only key mounts
- HUB has five network attachments and no host port mappings
- Every Sensor belongs to exactly one isolated Docker bridge and receives `HTTP 202 received_unverified`
- HUB ledger contains exactly the five unique identities; observations are **not** upgraded to verified attack claims
- Sensor-side Internet egress to 1.1.1.1:443 fails on internal networks, and a Sensor cannot resolve a different bridge's Sensor DNS name
- Guardian with `--network none` verifies a separately signed feed; no firewall changes or telemetry submission
- HUB loss does not cause alternate Internet report routing; lock remains as an operator-review safety gate

## Not proven / release HOLD

Five distinct Docker namespaces are **not five independent hosts, physical Raspberry Pis, operators, or Internet security domains**. A compromised Docker host can modify all nodes. External Witness key custody, real switch/VLAN/firewall policies, independent hub/Witness compromise, public ingress hardening, trusted software updates, and physical disk/power failure exercises are **not** covered.

No WAN listener, public Sensor enrollment, automatic blocking, port forwarding or changes to a production VPS are authorized by this experiment. The Draft PR must remain unmerged pending independent network assessment.
