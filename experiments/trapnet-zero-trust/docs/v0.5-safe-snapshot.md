# TrapNet v0.5: fail-closed capacity and offline snapshot

**Development only. Never expose HUB publicly.**

## Capacity
- `hub -max-ledger-bytes 67108864` defaults to 64 MiB (allowed: 1 MiB to 1 GiB).
- At cap the next report returns 507; it does NOT consume a replay ID, truncate evidence, or run automatic compaction.
- Exceeding configured cap at startup fails closed. Free disk space is NOT guaranteed by this cap.

## Safe snapshot procedure
1. STOP HUB, ensure the writer has exited, and investigate any stale `.lock` file. Never delete locks automatically.
2. Retain immutable backup of the original ledger and `.head`.
3. On HUB host, run `go run ./cmd/snapshot -ledger /secure/ledger.jsonl -out /secure/export/snapshot-0001`. Output must not already exist.
4. Snapshot tool takes the HUB writer lock, checks source chain/head, durably copies both files, verifies copy, and publishes the new directory atomically. If any check fails, there is no completed snapshot.
5. Transfer **both** copied files to a *separately administered off-HUB host* and attest with `cmd/witness`. Keep witness private key and pinned expected tip independently.
6. Keep the original ledger. Do not rotate/truncate without a future authenticated archive and replay-index protocol.

## Threat model and gaps
A malicious operator can bypass cooperative locks; privileged HUB control remains out of scope. No automatic recovery, witnessed retention, power-failure test, trusted timestamp, key rotation or multi-host isolation is claimed. Tests cover lock refusal, malformed and missing evidence, output existence, 507 and unchanged replay state. Production deployment and public enrollment stay HOLD.
