# TrapNet v0.9: VPS + Windows main-PC cross-host validation (2026-10-27)

**Status: two-host partial system test PASS; requested three-host system test BLOCKED on Stick PC interactive Windows login. Not a production or release approval.**

## Scope and trust boundaries

- Source revision: `f01527b498851b7b49b118fb18b2024a3f384c53` (draft PR #32).
- VPS: temporary sparse Git checkout and network-disabled, CPU/memory-bounded Go builder; an **independent disposable Docker container** ran the original loopback-only HUB with the v0.9 explicitly lab-only bridge. Docker network was created with `--internal`, and the only Docker port binding requested was **127.0.0.1**, not a public interface. The actual SSH forward used the Docker-internal container address because the localhost Docker published-port probe did not connect.
- Windows main PC: prebuilt Windows Guardian and public signing key transferred via authenticated SSH/SCP; signed feed checked offline. A temporary loopback SSH local forward carried synthetic HTTP POSTs to the VPS lab HUB.
- Stick PC: hostname resolved on LAN and RDP TCP port responded. RDP required interactive Windows credentials; **no login, agent installation, firewall change or Sensor execution occurred on this host**.
- **No real scanning, packet capture, malicious payload, auto-blocking, or production enrollment was performed.** The main PC only used a copied synthetic report as a temporary transport test, not as a live sensing service.

## Important limits

A correct Ed25519 signature identifies the signing key, not the truth of an observation. The report was pre-signed in a synthetic lab and transported from Windows; this **does not prove the Stick PC Sensor runtime** or a live event source. The lab's Docker host is shared with existing production workloads, so successful behavior is not a proof of independence against host compromise. The standalone v0.9 relay must never be used as public ingress. SSH host authentication and private-key custody need operator audit before broader testing. The test does not establish zero trust of a fully compromised VPS.

## Remaining physical 3-host gate

1. Authenticate to the Stick PC via its established RDP route and install a temporary **opt-in, one-shot, synthetic Sensor** there, using a new lab-only identity. No inbound listener or honeypot.
2. Establish outbound authenticated encryption from Stick to a *separately staged* HUB endpoint without opening a public port; isolate Stick from important PCs/NAS before any real exposure.
3. Repeat signed valid/forged/replay/expiry tests from Stick and verify the Guardian on the main PC continues functioning independently.
4. Run a truly independent network isolation and storage/power-loss rehearsal. Only after review consider hardware rollout.
