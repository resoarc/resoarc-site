# TrapNet v0.10: Windows host lateral-movement preflight

## What is established

The prior three-host test demonstrated signed Sensor -> HUB reporting and informational Guardian validation, **not** strong LAN isolation. The Stick PC and main PC currently share a home IPv4 subnet. A single non-authenticated direct TCP handshake from the Stick PC to a known listening RDP service on the main PC **succeeded**, demonstrating that home-LAN lateral reachability is possible. No credentials or application commands were sent.

The new read-only diagnostic is intentionally fail-closed: a successful direct connection is \`UNSAFE_DIRECT_REACHABLE\`, while an unsuccessful connection is only \`NOT_PROVEN\`. It **never** returns an isolation-approved status, because one closed port cannot rule out other lateral paths.

### How to reproduce safely

Run this only on your own Sensor host after explicitly choosing one protected RFC1918 IPv4 target and a known listening management port:

~~~powershell
powershell.exe -NoProfile -File .\lab\windows_isolation_preflight.ps1 -ProtectedTarget 192.168.1.101 -Port 3389 -OutputJson .\preflight-result.json
~~~

The address is a **sample**. Use the correct authorized local protected host. The audit makes **one** TCP handshake attempt, sends no credentials or data, touches no services and makes no firewall, route, or RDP changes. The JSON intentionally excludes raw IPs, usernames and secrets. Do not publish raw console command lines containing private addresses without removing them.

Exit codes:
- **2:** direct access observed, isolation failed for that route
- **3:** connection not observed, isolation **not proven**
- **1:** invalid input or audit failure, no trusted verdict

The module's offline test suite covers RFC1918-only input validation, false-pass prevention, same-prefix calculation, no side effects, and report minimization.

## Safe path to real isolation

1. Place an attack-facing Sensor on its own **router-enforced guest VLAN/SSID or physically isolated segment**, with deny rules toward the normal home LAN and NAS. A same-host Windows process firewall is not an adequate security boundary if the host is compromised.
2. Preserve a separate out-of-band recovery path before changing the network. **Do not change the existing Wi-Fi adapter, RDP port, router DHCP or default gateway remotely.**
3. Use a second independent host to establish a positive-control service that is known to be listening; a closed service is not evidence of VLAN protection. Test both guest->LAN denial and permitted encrypted Sensor->HUB egress after the router ACLs have been reviewed.
4. Keep Sensor-to-HUB as outbound-only with pinned endpoint/host key, independent node revocation and no public HUB listener; the Guardian stays read-only and offline verifiable.
5. Review home NAS and management exposure, host update status, incident recovery, consent and privacy before enabling any real attack capture or public enrollment.

**HOLD:** no physical/L2 or router-enforced separation has been proved on the Stick PC, so no real honeypot installation, general-public Sensor enrollment, firewall auto-reconfiguration, or production merge is authorized by this audit. The read-only audit is a readiness diagnostic only.

## Verified 2026-10-27 local results

- Windows PowerShell 5.1 offline regression suite: **18/18 pass** on the main PC.
- Stick PC audit: \`UNSAFE_DIRECT_REACHABLE\`, TCP port 3389 of a privately addressed main-PC management service reachable, shared IPv4 prefix observed; no network configuration altered. No IPs or secrets in published result.
- Main PC and Stick PC remained connected. This test was not a port scan or an external attack simulation.
