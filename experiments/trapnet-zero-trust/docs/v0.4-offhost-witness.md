# TrapNet v0.4: Off-HUB evidence witness (experimental)

**HOLD: not production ready. No Internet-facing HUB and no public Sensor enrollment.**

## Purpose
An attacker with privileged access to HUB could rewrite both the v0.3 evidence ledger and its local SHA-256 head. The new witness tool checks a closed snapshot of both files, signs the row count and digest on an **independent host**, and maintains a chained, signed history. An auditor holding the off-HUB history and public key can detect later edits to rows previously witnessed.

Cryptographic witnessing does NOT prove Sensor reports true. HUB may forge/omit evidence before first independent observation. Rows appended since the latest witness have not yet been externally certified.

## Independent offline workflow
1. Generate a separate Ed25519 keypair on the independent witness machine using the existing keygen. Never put the private witness key on HUB; do not reuse Sensor/Guardian keys.
2. Copy a consistent, **stopped/snapshotted** ledger.jsonl AND ledger.jsonl.head from HUB to the offline witness. Never witness a live append target.
3. Inspect a sample of the evidence, then attest:

    go run ./cmd/witness -mode attest -ledger /offline/ledger.jsonl -history /protected/witness-history.jsonl -key /secure/witness-keys/private.hex

4. Record the printed tip hash in a different independently controlled immutable/audited location. Protect the signed history and signing key off-HUB.
5. To audit a subsequent stable snapshot:

    go run ./cmd/witness -mode verify -ledger /offline/ledger.jsonl -history /protected/witness-history.jsonl -pub /secure/witness-keys/public.hex -expected-tip PINNED_TIP

## What the evidence demonstrates
- Tampering with previously witnessed rows is caught even after an attacker recomputes the local HUB checkpoint.
- Forged signatures, malformed/torn ledgers, missing heads, broken signed history order and repeated witness snapshots are rejected.
- An old but valid signed history can be replayed unless the auditor pins a trusted latest tip independently (expected-tip).
- The witness can check already attested prefixes even when newer evidence exists; newer rows remain unwitnessed until next attestation.
- This is a manual, offline process. It does NOT implement WORM storage, secure trusted timestamping, live witness peers, threshold trust, witness key rotation, bounded retention or automated privacy review.

## Incident response
If verification fails, halt new report intake; isolate HUB and preserve original ledger, head, signed witness history and independent published tip. Do not automatically repair or rebootstrap evidence. Examine separate backups and incident timeline before restoration. Examine a leftover .lock after crash instead of blindly removing it.

## Test scope
Run go test -race ./... and go vet ./... from experiments/trapnet-zero-trust. The five-identity test is entirely in-memory and does not establish five independent operator-owned network nodes or Sybil resistance.

**Draft PR only. Never enable broad automatic blocking, remote shell execution or public-facing collection based on this proof of concept.**
